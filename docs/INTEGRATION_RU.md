# Tviy.hub: как взаимодействуют фронтенд и бэкенд

Дата: 16 ноября 2026 года. Документ описывает интеграцию, без разбора обычной вёрстки.

## 1. Что сделано и что проверено

Фронтенд написан с нуля на React/TypeScript по предоставленной Figma. Контракты запросов сверены с Java-контроллерами, DTO и сервисами архива `TviyHub-backend-main.zip`. Ни один файл бэкенда не исправлялся. Побайтовая проверка 195 файлов относительно архива не обнаружила изменений; SHA-256 архива и результат сравнения записаны в `backend-integrity.json`.

Проверены TypeScript, production-сборка, 15 автоматических тестов API-клиента, правил брони и frontend-шлюза. В браузере проверены главная, изображения, переключение входа/регистрации, состояние недоступного API и мобильная компоновка при ширине iframe 390 px, из которых 375 px доступны содержимому из-за полосы прокрутки.

**Полный цикл с настоящим Java/MySQL не подтверждён.** Адрес работающего API не предоставлен; в среде выполнения нет Docker для запуска исходной MySQL-конфигурации. Автоматические тесты подменяют ответы `fetch` по контрактам Java. Это проверка поведения фронтенда, а не доказательство работоспособности Java-сервера, доставки писем или Stripe. Закрытые экраны профиля/админки реализованы и проходят компиляцию; интерактивная проверка с реальными ролями остаётся после подключения сервера.

| Файл | Ответственность |

Компоненты не формируют случайные URL самостоятельно. Например, кнопка вызывает `api.book(payload)`, а метод знает, что нужно отправить `POST /api/bookings`. Благодаря этому соответствие Java-контракту сосредоточено в одном месте.

## 3. Почему нужен прокси и как решён CORS

В архиве две настройки CORS. `WebConfig` читает `app.cors.allowed-origins`, но `SecurityConfig.corsConfigurationSource()` отдельно содержит `http://localhost:5173`. Поэтому одного изменения адреса во фронтенде недостаточно для прямого браузерного запроса с другого домена.

Решение сделано на стороне фронтенда: браузер обращается к своему же `/api`, а frontend-прокси пересылает запрос на Java-сервер. Для upstream-запроса он задаёт известный `Origin: http://localhost:5173`, который уже разрешён исходной защитой. Настройки и файлы Java не меняются. Сам прокси не заменяет вход: Java по-прежнему проверяет JWT и права на каждый закрытый запрос.

Есть три варианта одного решения:

| Среда | Кто принимает `/api` | Где задаётся адрес Java |
| --- | --- | --- |
| `npm run dev` | Vite | `API_PROXY_TARGET` в `.env.local` |
| frontend Docker/nginx | nginx | `API_PROXY_TARGET` в окружении контейнера |
| Опубликованный frontend-шлюз | Worker | серверная переменная `API_PROXY_TARGET` |

`VITE_API_BASE_URL=/api` остаётся одинаковым. `VITE_*` попадает в браузерную сборку, поэтому там нельзя хранить `JWT_SECRET`, пароли базы, SMTP или секрет Stripe. Адрес Java задаётся на стороне прокси.

В Worker-шлюзе пересылаются только нужные заголовки `Accept`, `Content-Type`, `Authorization`. Cookie домена фронтенда не уходят на Java; ответ `Set-Cookie` тоже не переносится обратно. JSON-ответы API не кешируются. Редирект API не выполняется автоматически. Без заданного адреса Java возвращается 503; при сетевом сбое upstream — 502.

Серверная часть frontend-шлюза нужна только для доставки файлов и проксирования. Бизнес-логика, база, JWT-проверка и создание брони остаются в предоставленном Spring Boot.

## 4. Вход, сессия и refresh token

При входе отправляется:

```http
POST /api/auth/login
Content-Type: application/json
```

```json
{"email":"user@example.com","password":"пароль из формы"}
```

Java возвращает `accessToken`, `refreshToken`, `tokenType`, `expiresInSeconds`, `refreshExpiresInSeconds`. Фронтенд добавляет своё `expiresAt = Date.now() + expiresInSeconds * 1000`, сохраняет сессию в памяти и `sessionStorage` текущей вкладки, затем получает реального пользователя через `GET /api/users/me`.

Роль берётся из ответа профиля, а не из введённого email. Кнопка админки показывается только для `ADMIN`; фактическое разрешение на запрос всё равно проверяет Java.

Защищённые запросы используют заголовок:

```http
Authorization: Bearer <accessToken>
```

Почему refresh сложнее обычного запроса: сервер вращает refresh token. После использования старый токен недействителен. Если профиль и история одновременно решили обновить его, два независимых refresh-запроса создали бы конфликт.

В `client.ts` для этого есть общий `refreshFlight`. Первый запрос создаёт Promise обновления, остальные ожидают тот же Promise. Новая пара токенов сохраняется один раз. Обновление происходит заранее, если до истечения access token осталось 15 секунд, либо после ответа 401.

После 401 исходный запрос повторяется максимум один раз. Если другой запрос уже сменил access token, новый refresh не запускается — используется новая пара. Повторный 401 завершает сессию. Ответы 403, 409 и сетевые ошибки не запускают автоматический повтор бизнес-запросов.

Если refresh отвергнут с 400/401/403, локальная сессия удаляется. При временной потере сети refresh token сохраняется, чтобы пользователь мог повторить попытку позже. Счётчик `revision` не даёт запоздалому refresh вернуть сессию после выхода. Закрытие вкладки завершает хранение в sessionStorage; это не отзыв токена на сервере.

При выходе локальная сессия очищается и выполняется `POST /api/auth/logout` с refresh token. Если сеть недоступна, локальный выход всё равно происходит, но серверный отзыв не подтверждён.

## 5. Регистрация и подтверждение почты

В Figma имя и фамилия раздельные, а `RegisterRequest` имеет одно поле `name`. Фронтенд объединяет их, убирает пробелы в начале/конце и отправляет `name`, `phone`, `email`, `password`. Из телефона удаляются пробелы, круглые скобки и дефисы; результат должен соответствовать международному формату `+380...`.

`POST /api/auth/register` возвращает профиль, **не токены**. Поэтому регистрация не считается входом. После неё открывается ввод шестизначного кода:

| Действие | Endpoint | Тело |
| --- | --- | --- |
| Подтвердить почту | `POST /api/auth/verify-email` | `{ email, code }` |
| Повторно отправить код | `POST /api/auth/resend-verification` | `{ email }` |
| Запросить сброс пароля | `POST /api/auth/forgot-password` | `{ email }` |
| Установить пароль по коду | `POST /api/auth/reset-password` | `{ email, code, newPassword }` |

Для повторной отправки после регистрации действует клиентская пауза 60 секунд. Это удобство интерфейса; ограничения частоты, срока кода и числа попыток контролирует Java. При 429 форма показывает сообщение и не начинает бесконечные повторы.

В исходном бэкенде при пустом `MAIL_HOST` код пишется в журнал приложения, а не отправляется на почту. Фронтенд не может организовать SMTP вместо Java. Пароли и коды не выводятся в консоль фронтенда. В приложении не встроен тестовый код подтверждения.

## 6. Каталог, доступность и реальные ID

`GET /api/workspaces` и `GET /api/tariffs` доступны без входа. Данные загружаются независимо через `Promise.allSettled`: сбой тарифов не уничтожает уже полученные места и наоборот.

В Figma пять столов, в миграциях архива — шесть столов и переговорная. Поэтому нельзя жёстко задать `workspaceId = номер кнопки`. Карта строится по ответу API; выбранный реальный `id` передаётся в каждый следующий запрос. До загрузки сервера показывается только схема со статусом «Немає даних» и неактивными местами.

Карта занятости запрашивается отдельно:

```http
GET /api/bookings/availability?date=2026-11-20&startTime=10%3A00&endTime=12%3A00
Authorization: Bearer <accessToken>
```

В текущем `SecurityConfig` этот GET не входит в публичный список. Поэтому гостю нельзя обещать свободное место: до входа статус неизвестен. Публичный список мест сам по себе ничего не говорит о занятости.

Ответ — массив `{ id, name, type, isAvailable }`. Свободным считается только явное `isAvailable === true`, не отсутствие записи и не отсутствие ошибки.

В блоке схемы сохранены поля даты, начала и длительности, кнопка «Оновити» и подпись выбранного интервала. Начальный интервал — ближайший будущий час. Легенда содержит только свободные и занятые места; подпись «Не перевірено» удалена, но неизвестное состояние не выдаётся за свободное. Параметры визита также можно изменить в форме бронирования.

При смене даты/времени прежняя карта очищается. `AbortController` отменяет неактуальный запрос; ответ старой даты не может перезаписать новую карту. Даже после успешной проверки доступность не гарантирована навсегда: другой пользователь может успеть забронировать слот. Окончательное решение принимает POST создания, а фронтенд обрабатывает 409.

## 7. Цена и создание бронирования

Для почасовой брони формируется Java `BookingRequestDto`:

```json
{
  "workspaceId": 3,
  "bookingType": "HOURLY",
  "bookingDates": ["2026-11-20"],
  "startTime": "10:00",
  "endTime": "12:00"
}
```

В каждой форме есть поле «Місце для бронювання», заполненное реальными рабочими местами из `GET /api/workspaces`. При открытии тарифа стол не выбирается автоматически; при открытии со схемы нужное место уже выбрано. Переключение места сбрасывает расчёт и заново запрашивает цену и доступность. Ответы отменённых запросов игнорируются; расчёт дополнительно привязан к ID места, формату, дате и времени, чтобы нельзя было отправить бронь с расчётом от прежнего стола. Для дневного и месячного форматов доступны только столы; переговорная остаётся почасовой. В запрос уходит ID выбранного ресурса, а не номер его подписи.

Хотя интерфейс выбирает один день, поле называется `bookingDates` и является массивом. Для дневной брони используется `DAILY`, поля времени не передаются; Java назначает 09:00–19:00. У переговорной доступен только `HOURLY`.

Перед отправкой выполняются две независимые проверки: `POST /api/bookings/calculate-price` и `GET /api/bookings/availability`. Расчёт возвращает JSON-число, а не `{ price: ... }`. Кнопка оформления неактивна, пока нет корректной суммы и явной доступности.

Цена обычной брони не вычисляется по надписям в Figma. Публичные карточки используют тарифы API, а итог в форме — ответ calculate-price. При отсутствии API публичные суммы отмечены как ориентировочные и оформить бронь нельзя.

Подтверждение отправляет `POST /api/bookings` с тем же payload. Ответ — **массив** `BookingResponseDto`; даже один созданный заказ нужно читать как `created[0]`. Успех показывается только после непустого ответа сервера. Итоговая сумма подтверждения берётся уже из `totalPrice` созданной брони. После успеха обновляется карта мест.

Нажатие блокируется на время отправки. При 409 место помечается недоступным и предлагается другое время. При сетевом timeout нельзя знать, успел ли сервер сохранить заказ: интерфейс предлагает сначала проверить историю. Автоматического повторного POST после timeout нет; сервер не предоставляет ключ идемпотентности.

Клиент проверяет будущую/сегодняшнюю дату, будний день, целые часы, диапазон 09:00–19:00 и длительность 1–4 часа. Эти проверки уменьшают число ошибок, но не заменяют Java-валидацию, проверку закрытых дней и конфликтов.

Дополнительно фронтенд запрещает начало брони в прошлом или в уже начавшийся час, сравнивая дату и время в `Europe/Kyiv`. Прошедшие часы отключены и в схеме, и в форме; по умолчанию выбирается ближайший будущий целый час, после закрытия — 09:00 следующего рабочего дня. Для `DAILY` начало фиксировано в 09:00: после этого времени предлагается будущий день либо почасовой формат. Абонемент остаётся календарным потоком с датой начала.

`useVenueClock` обновляет проверки каждые 15 секунд и при возвращении во вкладку. Непосредственно перед POST форма повторяет проверку по свежему времени, поэтому открытая заранее форма не позволяет отправить уже просроченный слот. В исходном Java API есть проверка прошлой даты, но отсутствует проверка прошедшего времени внутри сегодняшнего дня. Исходники Java не менялись: запрет реализован в интерфейсе, прямой запрос к API может его обойти. Уже созданные записи сохраняются в истории; availability по-прежнему берётся у сервера для выбранного интервала, а не подменяется на «свободно».

Даты передаются строками `YYYY-MM-DD`, время — `HH:mm`, без конвертации в UTC timestamp. «Сегодня» определяется в `Europe/Kyiv`. Это предотвращает смещение дня через `toISOString()` около полуночи. На Java используется `LocalDate/LocalTime`; часовой пояс его хоста при этом фронтенд не меняет.

## 8. Почему месячный абонемент — отдельный поток

Месячную подписку нельзя отправить обычным `POST /bookings` с `SUBSCRIPTION`: для неё отдельный `POST /api/subscriptions`:

```json
{"workspaceId":3,"startDate":"2026-11-20"}
```

Сервер сам определяет конец календарного месяца подписки, проверяет конфликты за весь период и возвращает `PENDING_PAYMENT`. Фронтенд показывает удержание, а не оплаченную активную подписку. Период берётся из `startDate/endDate` ответа. Самостоятельная покупка абонемента доступна роли USER, как в Java-контроллере.

Особенность архива: `SubscriptionService` создаёт платёж на фиксированные **3500 грн** и не читает тариф `SUBSCRIPTION` из таблицы. Поэтому клиент не подставляет потенциально отличающуюся цену из `GET /tariffs`: он отражает фиксированное поведение и показывает предупреждение, если справочник ему противоречит. Исправление бизнес-правила требует изменения Java и в эту работу не входило.

Отдельного endpoint проверки доступности на весь месяц и предварительного расчёта подписки нет. Поэтому наличие не обещается по карте одного дня: окончательная проверка происходит при создании. Подтверждение оплаты абонемента выполняется администратором через имеющийся backend endpoint; отдельный экран управления подписками в предоставленных макетах не реализовывался.

## 9. Профиль, история и повтор брони

История использует `GET /api/users/me/bookings?page=0&size=10&scope=all`. Варианты `scope`: `all`, `upcoming`, `past`. Это ответ `PageResponse` с `content` и `totalPages`, а не массив. Номер страницы начинается с нуля.

`BookingHistoryItem` содержит `workspace: { id, name, type }`, тогда как обычный `BookingResponseDto` содержит плоские `workspaceId/workspaceName`. Типы разделены намеренно: смешивание этих DTO приводит к undefined в карточке или неверному ID при повторе.

В истории поле `bookingDate` означает день визита, **не дату создания заказа**. Макетная подпись приведена к этому смыслу, потому что времени создания этот DTO не содержит.

«Повторити» открывает обычную форму с тем же местом и форматом на новый рабочий день. Старый POST не воспроизводится: заново проверяются доступность и цена. Отмена отправляет `PATCH /api/bookings/{id}/cancel`; после ответа история перезагружается. Сроки отмены контролирует Java, а его 400/403/409 показываются пользователю. В `BookingService.cancelBooking` проверка владельца и сроков выполняется только при роли, отличной от ADMIN. Поэтому ADMIN может отменять собственные и чужие подтверждённые обычные брони, включая прошедшие, без временного ограничения; повторная отмена уже CANCELLED-записи запрещена. В админ-панели кнопка отмены не фильтруется по дате или времени. Это проверено по исходникам сервера и интерфейса; исходники Java не менялись.

Для изменения имени достаточно `PATCH /api/users/me` с `{ name }`. Телефон и email этим методом менять нельзя. Для них и пароля используется два этапа:

| Поле | Запрос к `.../{field}/request` | Подтверждение |
| --- | --- | --- |
| `phone` | `{ newPhone }` | `POST .../phone/confirm` с `{ code }` |
| `email` | `{ newEmail, currentPassword }` | `POST .../email/confirm` с `{ code }` |
| `password` | `{ currentPassword, newPassword }` | `POST .../password/confirm` с `{ code }` |

Полный префикс — `/api/users/me`. Кнопки этих изменений требуют подтверждённого email. После смены телефона/email профиль читается заново. После подтверждённой смены пароля локальная сессия очищается: Java отзывает сессии, пользователь должен войти с новым паролем.

Аватар в макете декоративный; endpoint загрузки аватара в изученном профиле нет. Интерфейс показывает инициалы, не сохраняет изображение через выдуманный API.

## 10. Админ-панель и платежи

| Действие | API |
| --- | --- |
| Список клиентов | `GET /api/admin/users?page=...&size=10&search=...` |
| Данные клиента брони | `GET /api/admin/users/{id}` |
| Все брони | `GET /api/bookings` для ADMIN |
| Блокировать/разблокировать | `POST /api/admin/users/{id}/block` или `/unblock` |
| Отменить бронь | `PATCH /api/bookings/{id}/cancel` |
| Платежи | `GET /api/admin/payments` |
| Подтвердить наличные | `PUT /api/admin/payments/{id}/status` |

Вместо макетной кнопки удаления сделана честная блокировка. DELETE пользователя в API нет. Себя блокировать через интерфейс нельзя. В бронированиях нет имени клиента, только `userId`, поэтому для текущей страницы загружаются уникальные клиенты по ID.

Платёж связан с бронью через `payment.bookingId`, не через совпадение их ID. Админская кнопка подтверждения наличных находит соответствующий платёж и отправляет `{ status: 'PAID', paymentMethod: 'CASH' }` после явного подтверждения действия в интерфейсе. Она доступна только для неоплаченной подтверждённой обычной брони.

Для бронирований фронтенд отправляет `POST /api/payments/stripe-session/batch` с JSON `{ paymentIds, successUrl, cancelUrl }` и перенаправляет на Stripe по полю `url`. ID берётся из `paymentId` или `payment.id`. При повторной оплате фронтенд использует историю, а при отсутствии платёжных данных сопоставляет её с ответом пользовательского `GET /api/bookings`. Для абонементов используется существующий одиночный маршрут при наличии ID платежа.

Успешный возврат открывает `/payment/success`, отмена — `/my-bookings`. Фронтенд читает `session_id` и проверяет результат по `GET /api/payments/success?session_id=…` из той же вкладки и учётной записи. Для одного или нескольких платежей успех показывается, когда статусы всех ожидаемых ID — `PAID`. Поддерживаются отдельная запись, массив записей и объект с массивом `payments`.

Срок оплаты рассчитывается как более раннее из времени создания плюс 24 часа и начала брони. API может передать готовый срок через `paymentDeadline`. В архиве бэкенда `TviyHub-backend-main(3).zip` ответы не содержат ID платежа, времени создания или срока оплаты. Пакетного маршрута в этой версии нет. Кнопка онлайн-оплаты отключена, а при выборе администратора показывается правило срока. Перед боевым подключением Stripe серверу нужно проверять принадлежность всех платежей авторизованному пользователю.

## 11. Ошибки, отмена запросов и границы исправлений

API-клиент ожидает JSON и обрабатывает Spring `ProblemDetail`: `detail`, `title`, `errors`. Если сервер вместо JSON вернул HTML страницы приложения, это ошибка адреса/proxy, а не успешная загрузка каталога. Ответ 204 обрабатывается без попытки `response.json()`.

| Ответ | Реакция фронтенда |
| --- | --- |
| 400 | Показать сообщение/ошибки полей; исправить данные |
| 401 | Для защищённого запроса один refresh и один повтор |
| 403 | Не повторять запрос; показать отсутствие прав/необходимость подтверждения |
| 409 | Показать конфликт, не повторять запись автоматически |
| 429 | Сообщить о частых попытках, не устраивать цикл повторов |
| 502/503 или сеть | Показать недоступность, сохранить возможность ручного повтора |

Timeout клиента — 15 секунд. При изменении параметров чтения используется AbortController. При размонтировании компонента старый ответ не обновляет состояние. Мутации не заменяются оптимистическими «успехами»: подтверждение сервера обязательно.

Оставшиеся ограничения исходного сервера, которые нельзя честно устранить фронтендом:

- Фиксированная цена подписки вместо справочника.
- Отсутствие пакетного Stripe-маршрута и платёжных данных для клиента в проверенной версии бэкенда.
- Отсутствие DELETE пользователей, загрузки аватара и месячного availability endpoint.
- Доставка кодов зависит от SMTP Java.
- Лимитер входа использует адрес соединения; при серверном proxy клиенты могут делить один upstream-адрес и общий лимит. Фронтенд обрабатывает 429, но не подделывает IP, чтобы обходить защиту.
- Фактический часовой пояс Java-хоста и доступность Java из production/контейнерной сети задаются вне браузера.

## 12. Как проверить соединение после запуска настоящего API

1. Открыть фронтенд через Vite или frontend nginx. В Network проверить, что `/api/workspaces` и `/api/tariffs` возвращают JSON, а не HTML; карта должна показать реальные шесть столов, если начальные данные не менялись.
2. Зарегистрировать тестового пользователя. Получить код из письма либо журнала Java при dev-настройке без SMTP; подтвердить почту, войти. В Network проверить Bearer на `/users/me` и `/bookings/availability`.
3. Выбрать будний день, стол и два часа. Проверить payload `bookingDates`, `HOURLY`, `startTime/endTime`; сверить сумму calculate-price с суммой созданной брони.
4. Открыть историю. После повторного открытия страницы бронь должна прийти с сервера. Проверить отмену и повтор на новый день.
5. Войти существующим ADMIN, проверить пользователей и платежи. Не создавать новую ADMIN-роль на клиенте: роли назначает только сервер.
6. Проверить refresh после истечения access token; при параллельном открытии данных в этой вкладке должен уходить один refresh, не несколько.
7. Временно остановить Java. Убедиться, что интерфейс показывает ошибку, не рисует новые подтверждённые брони и не называет неизвестное место свободным.

Автотесты запускаются `npm test`. Для реального теста нужны работающий Java/MySQL, настроенная среда сервера и тестовые USER/ADMIN. Секреты бэкенда и реальные токены не нужно присылать в чат или помещать в исходники фронтенда.
